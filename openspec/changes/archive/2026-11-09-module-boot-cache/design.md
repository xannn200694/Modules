# Design

## Context

См. proposal.md, раздел Why. Сейчас старт читает `storage/app/modules.json`. Пока этот файл есть, манифест `module.json` в отборе не участвует. Код этого изменения не меняет поведение: документ только раскладывает уже принятый контракт по слоям.

## Goals / Non-Goals

**Goals:**

- Зафиксировать, что boot потребляет готовый кэш: отбор, порядок, провайдер, `autoload`.
- Отделить потребление кэша от его сборки, чтобы следующее изменение могло трогать `module:optimize` отдельно.

**Non-Goals:**

- Менять рантайм, команды `module:enable`, `module:disable`, `module:optimize` и генераторы.
- Описывать маршруты, представления и миграции внутри провайдера модуля.
- Делать алгоритм сборки кэша второй capability. В спецификации от него остаётся только исход холодного старта, когда файла кэша ещё нет.

## Decisions

### Контракт boot — существующий файл кэша

Boot отбирает модули из `storage/app/modules.json`. Альтернатива была считать контрактом `module.json`. Она отклонена: при живом кэше старт манифест не открывает, а `module:enable` и `module:disable` пишут только кэш.

Поля, которые решают загрузку: `enabled`, `order`, `slug`, `basename`, `autoload`. `name`, `version`, `description` и `id` в файле лежат, на отбор и на путь класса не влияют.

`slug` — ключ повторного поиска записи. Класс и каталог берутся из `basename` найденной записи и из настроенных `modules.namespace` и `modules.path`. Класс провайдера: `{namespace}{basename}\Providers\ModuleServiceProvider`.

### Отбор enabled — нестрогое равенство true

`enabled()` фильтрует коллекцию через `where('enabled', true)`. В `illuminate/support` 5.3.31 это сравнение `==`, не `===`. PHP приводит второе значение к boolean. Запись отбирают boolean `true`, число `1`, строка `"1"` и строка `"true"`. Непустая строка, кроме `"0"`, тоже равна `true`, включая строку `"false"`. Не отбираются boolean `false`, отсутствие поля, число `0`, строка `"0"` и пустая строка. Спецификация описывает это сравнение. Более ранний разбор исключал строку `"true"`; контракт следует коду и PHP `==`.

Альтернатива — зафиксировать строгое `===` и потом поменять код. Она меняет текущее поведение, а это изменение код не трогает.

### Сборка кэша остаётся производителем, не вторым контрактом старта

Пока файл кэша есть, boot его не пересобирает. Если файла нет, чтение создаёт пустой файл и сразу собирает кэш тем же путём, что `module:optimize`, после чего грузит уже построенный файл.

Сборка идёт по каталогам в `modules.path`. Ключ объекта — имя папки. В запись попадают `basename`, прежние поля кэша и поля манифеста; совпавшие ключи манифеста побеждают. Затем `id` всегда становится `crc32(slug)`. `enabled` дописывается из `modules.enabled` (иначе `true`), только если поля ещё нет. `order` дописывается как `9001` на том же условии.

Этот алгоритм объясняет холодный старт из спецификации. Пока кэш уже существует, boot его не применяет.

### Правка enabled не догружает текущий процесс

`module:enable` и `module:disable` переписывают `enabled` в файле кэша. Уже прошедший старт состав модулей не меняет. Новый состав виден следующему старту. Это прямое следствие решения читать кэш при boot, а не подписаться на файл.

## Risks / Trade-offs

- [Нестрогое `==` считает включёнными число `1` и непустые строки, включая `"true"` и `"false"`] → Спецификация называет это текущим поведением. Сужение до строгого `true` — отдельное изменение кода.
- [Две записи с одним `slug`] → Поиск возвращает первую по возрастанию `order`. Провайдер и путь могут взяться не из той записи, по которой шёл обход. Сейчас это не лечится.
- [Каталог модуля удалили, кэш не пересобрали] → Boot продолжает видеть старую запись. Пока класс и файлы не находятся, регистрация и `include` пропускаются.
- [Холодный старт читает манифесты] → Это единственный старт, где `module.json` влияет на состав. После появления файла кэша манифест снова молчит до следующей сборки.

## Migration Plan

Рантайм не меняется, выкладка и откат поведения не нужны. Артефакты живут в `openspec/changes/module-boot-cache/`. Откат записи — удалить этот каталог до архивации. После архивации capability попадёт в `openspec/specs/module-boot/`.
